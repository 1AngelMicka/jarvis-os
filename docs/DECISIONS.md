# Décisions techniques

## Installeurs complets (phase 14 · A, point 1)

- **Un contrat, deux scripts** : `install.ps1` et `install.sh` ont les mêmes étapes (uv, jarvis2, path, ollama, modele, preparation, demarrage), les mêmes options (forme `--oui` dans les deux ; `-Oui` reste accepté sous PowerShell), le même fichier d'état et les mêmes codes de sortie (0 installé, 1 étape en échec, 2 option invalide, 3 outil indispensable refusé ou impossible sans réponse). Le contrat est écrit en tête de chaque script.
- **Ce qui manque passe par le gestionnaire du système** : winget sous Windows, Homebrew sous macOS, sinon le script officiel de l'outil. Sous Windows, le PATH de la session est **relu depuis le registre** (machine puis utilisateur, dossiers de la session gardés) après chaque installation : la suite trouve `uv`, `jarvis2` et `ollama` sans rouvrir le terminal.
- **Fichier d'état** `installation.etat` dans le dossier de configuration (`JARVIS2_ETAT_INSTALLATION` pour l'essai et la CI) : texte `etape=statut` (fait, refuse, a_faire, echec), réécrit à côté puis renommé. Une étape « fait » est sautée à la relance ; l'installation de JARVIS est refaite si la source change ; `--recommencer` ignore le fichier. Rien d'autre n'y est écrit (ni chemin de l'utilisateur hors la source, ni secret).
- **Facultatif = proposé, jamais imposé** : Ollama et le premier modèle sont deux cases **décochées** ; `--oui` ne coche rien (il ne vaut que pour l'indispensable, uv), sans console rien n'est demandé ni coché, seul `--avec-ollama` les coche d'avance. Le modèle vient de la table matériel → modèle (`jarvis2 materiel --modele conversation`, nouvelle commande en lecture seule sur `materiel.py`) : aucune seconde table dans les scripts. Le script ne démarre jamais Ollama (règle 9) : s'il ne répond pas, le modèle reste « en attente » avec la commande à lancer.
- **Message final honnête** : un bilan par étape (présent, installé, déjà fait, refusé, non coché, en attente, ÉCHEC) et une liste « Reste à faire » ; un diagnostic qui signale des points à régler n'est pas présenté comme une réussite complète.
- **`--essai`** n'exécute aucune commande qui modifie quoi que ce soit, n'écrit pas le fichier d'état et ne va pas sur le réseau ; il ne fait que lire (présence des outils, fichier d'état, table matériel si `jarvis2` est déjà là).
- `irm … | iex` : le script PowerShell ne fait jamais `exit` dans ce cas (il fermerait la fenêtre) et rend son code dans `$LASTEXITCODE`.
- **CI** (`installeurs`, Windows, Ubuntu, macOS) : shellcheck, PSScriptAnalyzer, essais à blanc (PowerShell 5.1 et 7), installation non interactive depuis la roue du job `paquet`, puis relance qui doit tout reprendre du fichier d'état.

## Ressources et contrôle du PC (phase 13, lot J, migration 019)

- **Une seule porte vers Windows** : `pc/pilote.py` définit `PilotePC` (lire / régler) ; `pc/windows.py` l'implémente sans dépendance ni wmic (Core Audio par COM via ctypes pour le volume, DDC/CI par dxva2 puis WMI `Get-CimInstance` pour la luminosité, user32 pour les fenêtres et le verrouillage, contrôles multimédias du système par WinRT depuis Windows PowerShell 5.1, `shutdown /s /t` et `/a`, `powercfg`, registre de l'utilisateur pour les bannières de notification et le thème sombre, annoncé par `WM_SETTINGCHANGE`). Les valeurs passent aux scripts PowerShell par l'environnement, jamais dans leur texte. Les tests passent un faux pilote ; le vrai refuse en plus toute écriture quand `PYTEST_CURRENT_TEST` est défini.
- **Tout ce qui agit est une action du registre** (`pc.*`, `ollama.*`), donc file d'approbations, audit chaîné et arrêt d'urgence (une demande approuvée pendant l'urgence n'agit pas) : 🟢 `pc.etat`, `pc.extinction.annuler`, `pc.jeu`, `ollama.decharger` (lire ou protéger) ; 🟡 volume, sourdine, luminosité, fenêtres (premier plan, réduire, restaurer, fermer : jamais « toujours autorisé », c'est un clic à l'écran), média, verrouillage, modes, `ollama.demarrer` (jamais « toujours autorisé »), `ollama.arreter` ; 🔴 `pc.eteindre` (délai de 30 s à 1 h, 60 s par défaut, annulable jusqu'au bout ; l'arrêt d'urgence l'annule aussitôt par un rappel de `ArretUrgence`). Les routes `/v1/pc/*` ne font que lire.
- **Vérifié en relisant** (`pilote.verifier`) : après chaque réglage, l'état est relu quelques fois (Windows applique parfois avec retard) ; relecture impossible ou différente = « non vérifiée », avec la raison, jamais « fait » sur la seule foi de l'appel. L'extinction planifiée reste « non vérifiée » (Windows ne permet pas de la relire) ; son annulation est vérifiée par le code de `shutdown /a`. La file d'approbations affiche « vérifiée » / « non vérifiée » après l'exécution.
- **Modes qui changent vraiment Windows** : Jeu (plan d'alimentation Performances — `[pc] plan_jeu`, sinon les plans Performances de Windows, sinon un plan dont le nom l'évoque —, bannières coupées, veille stricte de JARVIS), Concentration (bannières coupées), Nuit (thème sombre, luminosité 30 %, volume ramené à 30 % au plus), Normal (remet exactement les réglages photographiés à l'entrée du premier mode, seulement ceux que JARVIS a changés). Mode et photo gardés dans `etat_systeme` (clé `pc`, migration 019). Ce qui n'existe pas sur le PC est sauté et dit (« aucun plan Performances », « luminosité non réglable »).
- **Ressources** sans wmic : CPU par `GetSystemTimes` (`/proc/stat`), RAM par `GlobalMemoryStatusEx` (`/proc/meminfo`) ; GPU et VRAM par `nvidia-smi`, sinon, sous Windows et pour toutes les marques (AMD compris), par les compteurs PDH « GPU Engine » et « GPU Adapter Memory » (ceux du Gestionnaire des tâches), sous Linux par `/sys/class/drm` ; VRAM totale par la détection du matériel. Historique de 10 min en mémoire seulement, mesuré toutes les 5 s **tant que la vue est regardée** (2 min après la dernière lecture), alerte au-delà de 80 %.
- **Ollama à la demande** (`pc/ollama.py`) : jamais démarré par JARVIS de lui-même (règle 9 inchangée) ; `ollama.demarrer` lance `ollama serve` (sans console, journal dans `journaux/ollama.log`) et attend jusqu'à 25 s qu'il réponde. JARVIS n'arrête **que l'Ollama qu'il a lancé** (un Ollama de l'utilisateur ou d'un autre programme n'est jamais tué : on décharge ses modèles), après `[pc] ollama_inactivite_min` (20 par défaut) sans modèle chargé (`/api/ps`), à l'entrée en veille et à l'arrêt du Core. Décharger = `keep_alive: 0`.
- **Mode jeu = veille stricte** (`pc/jeu.py`) : automatique (défaut), forcée ou jamais. Détection toutes les 3 s de la fenêtre au premier plan : programme dans un dossier de jeux connu (Steam, Epic, Riot, Ubisoft, EA, GOG, Xbox, Battle.net) ou dans `[pc] jeux`, ou plein écran hors navigateurs et lecteurs vidéo ; veille après 5 s de jeu, réveil 20 s après. En veille : modèles déchargés, Ollama de JARVIS arrêté, recettes planifiées en attente (elles partent au réveil), rien ne redémarre seul. Sans écran : pas de détection, la veille forcée reste possible.
- **Mode sans écran** : les actions de contrôle du PC ne sont pas proposées (prédicat `disponible`) et refusent d'agir ; `/v1/pc/etat` répond 409 (`garde_ecran`). Ressources, Ollama et mode jeu forcé restent utilisables.
- **Vision : OCR d'abord** (`ocr.py`, `vision.analyser`) : l'OCR intégré à Windows (Windows.Media.Ocr, langues de l'utilisateur ; `tesseract` ailleurs) lit l'image ; s'il y a assez de texte (40 caractères et 6 mots), la réponse est ce texte, sans réveiller de modèle. Sinon seulement, le modèle de vision local décrit l'image (le peu de texte lu lui est donné comme donnée). Si Ollama est arrêté, rien n'est démarré : la réponse le dit (`ollama_requis`). `forcer_modele` passe l'OCR. Fichier temporaire de l'image effacé aussitôt.
- Interface : catégorie « PC & mode jeu » des Réglages (`#reglages/ressources-pc`, `mode-jeu`, `controle-pc`), qui ne fait qu'appeler `/v1/pc/*` et `/v1/actions`.

## Connecteurs maison Hue et OBS (phase 14 · D, point 17, migration 013)

- **Désactivés par défaut**, activés à la main dans Connecteurs → Maison (table `connecteurs_maison` : état et adresse). La clé du pont Hue et le mot de passe d'OBS vivent dans le coffre local (`maison.hue`, `maison.obs`), jamais en base, dans les réponses ni dans l'audit. « Oublier » retire le secret et désactive.
- **Commandes = actions du registre** (`hue.*`, `obs.*`) : 🟢 `hue.etat`, `obs.etat` ; 🟡 allumer, éteindre, luminosité, couleur, scène Hue, scène OBS, enregistrement, arrêt du direct ; 🔴 `obs.direct.demarrer` (publication : clé d'accès). Elles passent par la file d'approbations et l'audit chaîné, et refusent d'agir pendant l'arrêt d'urgence, même approuvées. Une action porte désormais un prédicat `disponible` : celles d'un connecteur désactivé n'apparaissent pas dans `/v1/actions` ni dans `outils_actifs` de `/v1/maison` (la liste à proposer au dialogue), et une demande créée avant la désactivation échoue à l'approbation.
- **Hue** : API v1 locale du pont en HTTPS. Le certificat du pont est signé par l'autorité de Signify, absente des magasins du système : il n'est pas vérifié ; en contrepartie seules les adresses privées sont acceptées, la clé ne part donc jamais sur Internet. Découverte par mDNS (`_hue._tcp.local`, TTL 1) ; le service en ligne `discovery.meethue.com` seulement si l'utilisateur coche l'accord (entrée d'audit 🟡), adresses publiques écartées. Appairage : bouton du pont puis `POST /api` (clé « username »).
- **OBS** : WebSocket v5 (OBS 28+), une connexion courte par commande, sans abonnement aux événements ; mot de passe jamais envoyé en clair (empreinte SHA-256 sel + défi). Client WebSocket minimal écrit dans `maison/websocket.py` plutôt qu'une dépendance (texte seulement, réponses aux ping). Adresse : bouclage ou réseau local.
- Le dialogue n'a pas encore d'appel d'outils natif : les commandes se déclenchent par `/v1/actions` ; `outils_actifs` est la liste à brancher quand il en aura un.

## Home Assistant, Wyoming, satellites, profils (phase 14 · D, point 18, migration 026)

- **Le PC reste le cerveau** : JARVIS décide et fait approuver ; Home Assistant exécute. Connecteur désactivé par défaut, réglages dans `etat_systeme` (`home_assistant`, ligne créée par la migration, écrite par `UPDATE` seulement) plutôt que dans `connecteurs_maison`, dont la contrainte `CHECK` n'accepte que `hue` et `obs` (la changer sous SQLite demanderait de reconstruire la table). Adresse : réseau local, Tailscale ou ce PC (`flux_donnees.destination_url`), jamais Internet.
- **MCP d'abord, REST en repli** : client MCP « streamable HTTP » écrit dans `maison/home_assistant.py` (le client de `agents/mcp.py` ne parle que stdio) : `initialize`, `Mcp-Session-Id`, réponses JSON ou SSE. Jeton par le flux OAuth de Home Assistant avec PKCE S256 (`client_id` = adresse de bouclage du Core, retour sur `/v1/maison/home-assistant/oauth/retour`, seule route publique ajoutée : `state` à usage unique de 10 min, vérifieur jamais transmis avant l'échange). Jeton de rafraîchissement au coffre ; jeton d'accès en mémoire vive seulement. Sans MCP joignable, lecture par REST si un jeton longue durée est rangé.
- **Les niveaux viennent du domaine** (`DOMAINES`), pas de Home Assistant ni du modèle : 🟢 état, 🟡 `light` / `switch` / `media_player`, 🔴 `lock` / `alarm_control_panel` / `cover` de type `gate` ou `garage` (autres couvertures refusées). Chaque action n'accepte qu'une entité de son domaine ; avec un jeton REST, l'entité est relue avant d'agir (type de couverture). Les outils MCP de Home Assistant (`HassTurnOn`…) ne sont jamais proposés tels quels : seules nos actions les appellent, avec `domain` imposé. L'alarme passe par REST seulement (pas d'outil MCP équivalent) ; son code reste au coffre, lu au moment d'agir.
- **🔴 = clé d'accès + voix du propriétaire** : nouveau champ `Action.garde`, appelé avant de créer la demande (« demande ») et juste avant d'agir (« execution »). Reconnaissance coupée ou indisponible : refus aux deux étapes ; à la demande, une phrase reconnue du propriétaire dans les 2 dernières minutes (`proprietaire.derniere_reconnue`) est exigée. Refus journalisé `maison.rouge_refusee`. Le service Home Assistant du déverrouillage n'est pas un nom d'action : la règle « aucune action de déverrouillage » du registre (session du PC, téléphone) ne change pas.
- **Wyoming** (`maison/wyoming.py`) : protocole réimplémenté (ligne JSON + données + charge, tailles bornées), sans la bibliothèque `wyoming` ni wyoming-satellite (archivé). Désactivé par défaut, écoute sur 127.0.0.1 sauf choix de l'utilisateur (adresse privée ou toutes les interfaces). Accès : clients Wyoming ordinaires (Home Assistant) depuis ce PC ou une adresse IP autorisée ; satellites par l'événement d'extension `jarvis-satellite` (identifiant + clé, empreinte SHA-256 comparée à temps constant). Audio reçu en PCM, remis en WAV pour `TranscripteurRobuste` (l'observateur du propriétaire s'applique donc aussi aux satellites).
- **Satellites** : l'éveil se fait sur l'appareil ; avant `detection` / `run-pipeline`, tout `audio-chunk` est jeté sans être lu. Déblocage à 25 s, phrase de 30 s au plus, connexion fermée après 5 min sans événement. Minuteurs reconnus par une expression régulière (« minuteur / timer de N secondes|minutes|heures »), sans IA, envoyés en `timer-started` / `timer-finished` à la session du satellite d'origine (retrouvée par son identifiant s'il s'est reconnecté). Plafond de volume appliqué aux échantillons (le plus bas du satellite et du profil). Les autres phrases passent par le dialogue normal (`Contexte.repondre_satellite`) : les actions restent des demandes à approuver.
- **Présence et profils** : `satellites_maison.vu_le` et `personne` (propriétaire, profil ou rien), jamais le texte ; pièce occupée 10 min. Profils dans `profils_voix` (nom, plafond de volume), empreintes dans `voix/empreintes.json` avec le champ `profil`. Une phrase plus proche d'un profil que du propriétaire est « inconnue » : un profil n'ouvre jamais une action 🔴.
- **Reporté** : essai sur un vrai Home Assistant et de vrais satellites (tout est testé avec de faux serveurs) ; firmware ESPHome qui envoie `jarvis-satellite` (les satellites passés par Home Assistant marchent sans) ; rattachement des satellites gérés par Home Assistant à une pièce (Home Assistant ne transmet pas l'appareil dans une requête Wyoming).

## Barrière d'injection par tour (phase 14 · B, point 6)

- **Un seul endroit** : `securite/barriere.py`. Un **tour** = une réponse du dialogue (recettes comprises, elles passent par le dialogue), une réponse du conseil multi-IA, une mission, une exécution d'atelier (une consigne). Le tour courant vit dans une variable de contexte asyncio (`with barriere.tour(...)`), sauf pour les ateliers, dont les autorisations arrivent par des requêtes HTTP séparées : leur `Tour` est tenu par jeton d'exécution et passé explicitement.
- **Sources qui contaminent** (chacune appelle `barriere.marquer`) : recherche web (`RechercheWeb.chercher`), sources scientifiques, résultat d'outil MCP (`GestionnaireMCP.appeler`), image lue (OCR ou vision, `vision.analyser`), image jointe au message, partage reçu (balise `<contenu_recu non_fiable>`, dans le message ou plus haut dans la conversation), fiches de connaissances mises en contexte (écrites depuis des rapports de mission), avis des experts du conseil (sortie d'autres sessions) ; dans un atelier, WebFetch, WebSearch, tout outil `mcp__…` (sauf celui de JARVIS) et toute lecture hors du worktree accordée par l'utilisateur. Hors de tout tour (lecture demandée depuis l'interface), `marquer` ne fait rien.
- **Ce qui est refusé** : toute action 🟡 🔴 du registre et les 🟢 marquées `Action.ecrit` (`pc.jeu`), refusées dans `Approbations.demander` avant même les règles et le « toujours autorisé » ; les propositions du pilotage autres que `naviguer`, `ouvrir`, `rechercher_memoire` (marquées `bloquee`, jamais appliquées seules, même en mode « oui ») ; dans un atelier, tout outil hors lecture (écriture, Bash, outil MCP, inconnu), refusé sans même demander. Les 🟢 protectrices (`pc.extinction.annuler`, `ollama.decharger`) restent permises : elles ne font que retirer un risque.
- **Chaque refus** : raison en français qui nomme les sources lues et invite à relancer l'action soi-même ; entrée d'audit 🟡 `barriere.action_refusee` (cible = action ou outil, détails = genre du tour, identifiant et **types** de sources, jamais le détail lu) ; meta `barriere` du message (sources, actions retenues, message), montrée sous la réponse ; événement `barriere` du fil d'un atelier, résultat `barriere` d'une mission.
- **L'utilisateur n'est jamais bloqué** : un clic depuis l'interface passe par une route ordinaire, hors de tout tour. Le tour suivant repart sain (la variable de contexte est rendue à la sortie du bloc ; le jeton d'atelier est retiré avec son exécution).
- **Lectures toujours permises**, WebFetch compris dans un atelier (l'utilisateur l'accorde en direct, comme avant) : la barrière vise les actions, pas la consultation. Pas de migration : rien n'est stocké en dehors de la meta des messages et de l'audit.
- Origine de l'idée : ASD (voir INSPIRATIONS.md), et le principe « contenu externe = donnée, jamais instruction » de CLAUDE.md, rendu mécanique.

## Détecteur d'« exécution inventée » (phase 14 · B, point 8)

- **Signaler, jamais corriger** : la réponse reste telle que le modèle l'a écrite ; le signalement va dans la meta du message (`invente`), un événement SSE `invente` après `fin`, et l'audit (🟡 `dialogue.execution_inventee`, cible = message ou mission, détails = catégories et verbes seulement, le texte pouvant être privé).
- **Journal réel du tour** = entrées d'audit écrites entre le début et la fin de la réponse (repère : dernier identifiant d'audit), plus les outils que le moteur déclare dans `meta["outils"]`. Ne comptent pas : une action en échec, une simple demande (`demande.*`), un signalement précédent. Une action d'une autre catégorie n'appuie pas l'affirmation (supprimer ≠ envoyer), sauf un outil au sens inconnu (MCP, action enregistrée au nom non reconnu) qui appuie tout : mieux vaut rater une invention que crier au loup.
- **Règles plutôt que modèle** : expressions régulières sur des verbes d'action (envoyer, supprimer, lancer, installer, payer, programmer…), sans appel à une IA (rapide, déterministe, local). Faux positifs écartés : futur, conditionnel, négation, questions, hypothèses (« si », « par exemple »), citations et code ; les verbes qui servent aussi à travailler le texte (créer, ajouter, modifier, supprimer…) n'entrent en compte qu'avec un objet concret (fichier, rappel, agenda…) et jamais quand la phrase montre le résultat (« voici », « ci-dessous ») ou que la réponse contient du code. Lire et chercher ne sont pas des actions à vérifier ; « j'ai bien enregistré votre demande » non plus (politesse), mais « j'ai enregistré votre préférence dans ma mémoire » oui (aucune écriture en mémoire pendant le tour).
- Le détecteur ne bloque jamais une réponse : audit illisible ou erreur = pas de vérification pour ce tour (journalisé).

## Matériel → modèle (phase 14 · A, point 3)

- **Une seule table** (`materiel.TABLE`) : pour chaque usage (conversation et vision par Ollama, embeddings, transcription Whisper), des paliers « mémoire nécessaire → modèle ». Le conseil prend le plus gros palier qui tient puis **descend d'un palier** pour garder de la marge (contexte long, autres programmes) ; le maximum est montré à titre indicatif. Exception : les embeddings (taille fixe, chargés une fois) ne descendent pas.
- **Mémoire utile** : VRAM de la carte si elle accélère (CUDA, ROCm, Vulkan) et dépasse 4 Go ; Apple Silicon : 70 % de la mémoire unifiée ; sinon la moitié de la RAM, avec un plafond de 7 à 9 milliards de paramètres (lenteur du processeur). Whisper et les embeddings tournent sur le processeur : leur budget est la RAM.
- **Détection** sans dépendance ni wmic : RAM par `GlobalMemoryStatusEx` (Windows), `/proc/meminfo`, `sysctl hw.memsize` (macOS) ; `nvidia-smi` puis `rocm-smi` s'ils existent ; sinon le registre des cartes graphiques (Windows, toutes marques, valeur 64 bits) ou `/sys/class/drm` (pilote amdgpu). Une carte AMD RX 6800 et plus, RX 7000, RX 9000 est comptée ROCm (Ollama embarque ses bibliothèques), les autres Vulkan. Une seule détection par lancement du Core.
- Exposé par `GET /v1/materiel`, `jarvis2 docteur` (ligne « Matériel et modèles locaux ») et la famille « locale » de la page Connecteurs. Rien n'est jamais téléchargé ni démarré : les noms sont des conseils.

## Application de bureau et publication (phase 11)

- **Coque Tauri 2** (`app/`) : une fenêtre sur l'interface du Core local ; le Core n'est pas embarqué (installé par le script, `uv tool install`) : l'application le lance s'il ne tourne pas (sans console) et n'arrête que celui qu'elle a lancé. L'interface est une page distante pour l'application : aucune permission native (`capabilities/default.json` vide). Icône de notification (Ouvrir, Quitter), fermer = cacher, Ctrl+Maj+J, une seule instance.
- **Construction** sur GitHub Actions (`publication.yml`) : à une étiquette `v*`, roue du Core + installeurs Windows (NSIS, MSI), macOS (DMG), Linux (DEB, AppImage), déposés dans une version **en brouillon** (rien de public avant que le propriétaire la publie). Signatures par secrets du dépôt, facultatifs : clé de mise à jour Tauri, certificat Windows, certificats et notarisation Apple.
- **Installation en une ligne** : sans `-Source` et hors d'un dépôt, les scripts prennent la roue de la dernière version publiée (`releases/latest`).
- Construction locale impossible sur un disque exFAT (Cargo ne peut pas y fixer les dates des fichiers) : elle se fait sur GitHub.

## Sauvegarde et bascule (phase 12)

- **Archive** (`sauvegarde.py`) : `JARVIS2S1` + sel scrypt (n = 2¹⁵) + nonce + AES-256-GCM d'un tar.gz (base, `config.toml`, recettes, manifeste). SQLite : copie cohérente par l'API de sauvegarde de SQLite ; PostgreSQL : `pg_dump -Fc` dans le conteneur. Le coffre des clés d'API n'est pas inclus (chiffré par Windows pour ce compte et ce PC). Écriture atomique (`.partiel` puis renommage), rotation des 7 dernières.
- **Vérification** : déchiffrement, restauration dans une base temporaire (fichier temporaire ou base `jarvis2_verification_sauvegarde`, effacée ensuite), comparaison au manifeste (lignes des tables principales, chaîne d'audit et dernière empreinte).
- **Rattrapage** : l'import `jarvis_v1` est rejouable (aucun doublon) ; à lancer avec la dernière sauvegarde quotidienne de JARVIS v1, copiée en lecture seule.

## Voix, vision, créations (phase 10)

- **Transcription locale** (`voix.py`) : faster-whisper sur le CPU (int8), modèle téléchargé une fois dans `<données>/modeles/whisper` ; l'audio (webm/opus du navigateur, wav…) est décodé par PyAV puis rééchantillonné à 16 kHz par JARVIS (l'appel de PyAV dans faster-whisper n'est plus compatible avec PyAV ≥ 15). Invite initiale « Jarvis » pour l'orthographe du nom ; mot d'éveil tolérant (« j'arvi », « djarvis »…).
- **Synthèse vocale** dans l'interface : `speechSynthesis` avec une voix française **locale** seulement (`localService`) ; sans voix locale, rien n'est lu (jamais de voix en ligne). Lecture phrase par phrase pendant le flux.
- **Mains libres** : détection de la parole par le niveau sonore (phrase = parole puis 0,9 s de silence, 15 s au plus) ; chaque phrase est transcrite sur le PC et ignorée sauf si elle commence par « Jarvis » (ou suit un « Jarvis » seul dans les 8 s). L'écoute est suspendue pendant que JARVIS parle ou répond.
- **Vision** (`vision.py`) : seulement sur demande, à partir d'une capture que l'utilisateur déclenche et choisit (`getDisplayMedia`) ; décrite par le modèle local `[connecteurs.ollama] modele_vision` ; l'image n'est ni gardée ni envoyée ailleurs.
- **Créations** (`creations.py`) : page HTML générée par le routeur (IA locale pour un sujet privé), servie par `/creations/<id>?v=&j=` avec un jeton HMAC de 10 minutes (secret propre au démarrage) et la CSP `sandbox allow-scripts …; default-src 'none'; connect-src 'none'; frame-ancestors <origine de l'interface>` : origine unique (aucun accès à l'interface, aux jetons ni au stockage), aucune requête réseau. `frame-ancestors 'self'` ne convient pas : sous `sandbox`, il désignerait l'origine opaque de la page.

## Dialogue avancé (phase 13, lot E)

- **Images jointes** : préparées dans le navigateur (`interface/src/images.ts`) : JPEG, PNG, WebP, GIF ; 5 par message ; au-delà de 1 600 px ou 1 Mo, réduites et recompressées (JPEG reste JPEG, PNG et WebP en WebP, ou JPEG si le navigateur n'écrit pas le WebP ; 85 %) ; GIF jamais redimensionné, refusé au-delà de 3 Mo. Le Core revérifie tout (`vision.decoder_jointe` : type lu dans les premiers octets, jamais l'en-tête annoncé ; SVG refusé ; 3 Mo au plus).
- **Rien n'est gardé** : les images vivent en mémoire le temps de la réponse ; l'historique ne garde que leur nombre, leur type et leur poids (`meta.images`), et les messages suivants disent seulement au modèle qu'il y en avait. Seule exception, Claude Code (CLI) : les images sont écrites dans un dossier temporaire du système (`jarvis2-images-*`), dossier de travail de la CLI avec l'outil `Read` pour seul outil (lecture dans ce dossier seulement), effacé dès la fin de la réponse, même en cas d'erreur ou d'annulation. L'interface garde les miniatures dans la page tant qu'elle reste ouverte.
- **Moteurs** : API Anthropic (blocs `image` en base64), compatibles OpenAI (parties `image_url`), Ollama (`images` ; si le modèle choisi n'a pas la capacité « vision » annoncée par `/api/show`, le `modele_vision` de la configuration locale prend le relais, sinon message clair). Codex et Antigravity : pas de vision, refus clair avant tout envoi. Le routeur ne choisit qu'un connecteur qui lit les images ; un sujet privé reste sur une IA locale. Le filtre des secrets ne s'applique pas au contenu d'une image : l'utilisateur la joint lui-même.
- **Palette et commandes** : une seule liste (`interface/src/commandes.ts`) pour la palette Ctrl+K, les commandes « / » de la saisie (« // » envoie un texte qui commence par « / ») et l'aide (`?` ou `/aide`). Raccourcis Ctrl+K, Ctrl+H, Ctrl+M ; l'arrêt d'urgence demande toujours une confirmation. Fenêtres en `<dialog>` modal (focus piégé puis rendu, Échap ferme sans arrêter la réponse en cours).

## JARVIS pilote l'interface (phase 13, lot F, migration 014)

- **Bloc d'actions validé par le Core** (`pilotage.py`) : quand l'utilisateur le demande, le modèle finit sa réponse par `<actions>[…]</actions>` (JSON). Le Core retire le bloc du texte (l'interface le masque déjà pendant le flux : ni affiché ni lu à voix haute), valide chaque action contre une liste fermée (vues connues, identifiants qui EXISTENT en base, longueurs, actions déclarées), applique les règles de protection, et range le reste dans `actions_ecartees` (raisons seulement). Aucun shell, aucun type inventé ne passe.
- **Deux genres** : `immediate` (naviguer, ouvrir une conversation / mission / création / atelier, chercher dans la mémoire, thème ou animations) et `proposition` (mission, atelier, action déclarée 🟡🔴, règle). Mode `pilotage` (`etat_systeme`) : « oui » = l'immédiate s'applique seule à la fin d'une réponse en direct (une seule navigation, jamais en relisant l'historique), « demander » (défaut) = bouton, « non » = aucune consigne et tout bloc écarté. Les propositions sont **toujours** un bouton : protection contre l'injection (un souvenir importé, une page lue ne peut rien lancer). Le clic passe par les routes habituelles (`POST /v1/missions`, `/v1/ateliers`, file d'approbations, `/v1/regles`).
- Une action proposée n'est pas une action faite : l'audit `pilotage.actions` (types et nombre d'écartées, jamais le contenu) est ignoré par le détecteur d'exécution inventée.
- **Motifs à jokers** (`securite/jokers.py`) : `*` et `{nom}`, comparés sans accents, majuscules ni ponctuation ; jamais d'expression régulière fournie par l'utilisateur (chaque partie littérale est échappée), au moins deux lettres ; les captures reprennent le texte d'origine (accents gardés).
- **Commandes rapides** (`commandes_rapides.py`) : phrase ENTIÈRE ↔ motif → action d'interface (🟢, sans rien lancer) ou action déclarée du Core, qui passe par la file d'approbations (🟢 exécutée, 🟡 demandée, 🔴 clé d'accès) : une commande ne donne aucun droit en plus, jamais de shell. Priorité −100 à 100, puis le motif le plus précis, puis le plus ancien ; phrase de test obligatoire, vérifiée à l'enregistrement et en direct dans l'éditeur (conflits signalés). L'interface essaie la commande avant l'IA (phrase ≤ 300 caractères, sans image, hors conseil) ; sinon la phrase part à l'IA.
- **Règles de protection** (`securite/regles.py`) : « interdire » (refus, même d'une demande déjà en attente) et « demander » (impose une demande, même pour une action 🟢 ou toujours autorisée). Le motif est cherché n'importe où dans le nom, le résumé et les paramètres. Ajouter = 🟢 (protège) ; retirer = action `regle.supprimer` 🟡, jamais « toujours autorisable », et les actions sur les règles échappent aux règles (sinon une règle ne se retirerait plus). Les règles sont données au modèle (sauf celles qui nomment un sujet exclu : filtrées par l'expurgateur) ; l'audit n'en garde jamais le motif.
- **« Toujours autoriser »** (`autorisations_permanentes`) : case sous une demande 🟡 dont l'action est `autorisable` ; la suivante s'exécute sans demande (audit « (toujours autorisé) », compteur d'utilisations). Jamais pour 🔴 (refus, même avec une clé d'accès, et une ligne insérée de force est ignorée), ni pour `mcp.appeler` (un outil peut cliquer, naviguer, écrire) ni pour un futur clic à l'écran ou dans un navigateur (`autorisable=False`). 🔴 reste approuvé par clé d'accès sur chaque appareil, donc jamais à distance sans elle. Retirer = 🟢.
- Pendant l'arrêt d'urgence, retirer une autorisation et ajouter une règle restent possibles (elles protègent).

## Ateliers Claude Code (phase 9, migration 009)

- **Binaire officiel plutôt que le SDK** : `claude -p --output-format stream-json` dans le worktree, environnement sans clés d'API, réponse refusée si `apiKeySource` ≠ `none` (même règle que le connecteur). Les ateliers exigent l'avertissement Claude Code accepté.
- **Isolation** : `git worktree add -b jarvis/atelier-<id>` dans `<données>/ateliers/<projet>/`, depuis le HEAD du projet ; le projet n'est touché qu'à la fusion.
- **Autorisations** (`ateliers/autorisation.py`) : Claude Code appelle avant chaque outil `mcp__jarvis__autoriser` (`--permission-prompt-tool`), servi par `jarvis2 atelier-mcp` (stdio) qui relaie au Core (`POST /v1/ateliers-autorisation`, boucle locale seulement, jeton aléatoire propre à chaque exécution). Écriture : autorisée dans le worktree (chemins résolus), refusée ailleurs, ainsi que dans `.git` et les `.env` ; lecture hors du worktree, commandes, réseau, autres outils : décision de l'utilisateur en direct (refus au bout de 10 minutes). Chaque décision est notée dans le fil de l'atelier.
- **Fusion** : action 🟡 `atelier.fusionner` — JARVIS commite le worktree (auteur « JARVIS »), puis `merge --no-ff` dans le projet s'il est propre ; en cas de conflit, `merge --abort` (projet inchangé). Abandon : le worktree est retiré, la branche reste.
- **Projets** : `[[ateliers.projets]]` (id, nom, chemin) de la configuration locale. Limite connue : git refuse un dépôt sur un disque sans propriétaires (exFAT) tant que `safe.directory` ne l'autorise pas.

## Ateliers, suite (phase 13, lot I, migration 015)

- **Pause réelle** : le processus de Claude Code est suspendu (`NtSuspendProcess` sous Windows, `SIGSTOP` à son groupe ailleurs) et ses demandes d'autorisation attendent la reprise : rien ne lui est accordé pendant la pause, même une commande lancée avant (Windows) qui finirait seule. Une pause reste en mémoire du Core (un Core redémarré n'a plus de processus à reprendre).
- **Relance** : un plantage technique (code de sortie ≠ 0 sans résultat) relance Claude Code au plus 2 fois, dans la même session, avec la fin de sa sortie d'erreur (secrets masqués) notée dans le fil (`<données>/ateliers/journaux/`) ; un échec rendu par Claude Code met l'atelier en « Erreur », et « Relancer » renvoie la dernière consigne dans la même session.
- **Modèle** : colonne `modele` (alias `sonnet` / `opus` / `haiku` ou identifiant complet, motif strict), passé en `--model` ; vide = réglage de Claude Code.
- **Conflits** : table `fichiers_atelier` (fichiers écrits via Write/Edit, plus ceux que git voit modifiés ou commités à la fin de chaque exécution, donc aussi par une commande) ; deux ateliers ouverts du même projet sur un même fichier sont signalés dans les deux fils et dans la vue, jamais bloqués (la fusion garde son `merge --abort` en cas de vrai conflit).
- **Clôture** : notes libres + `clos_le` ; le travail non commité l'est sur la branche, puis le worktree est retiré : rien n'est perdu. Un atelier clôturé sort des résumés, de l'Activité et des conflits.
- **Ce qui tourne dans le contexte** : à chaque échange, ateliers actifs, en pause, en échec ou en conflit, sessions Claude Code veillées et missions en cours, en quelques lignes (états seulement, jamais le contenu des fils), passés par l'expurgateur des sujets exclus.
- **Veille des sessions Claude Code de l'utilisateur** (`ateliers/veille.py`) : désactivée par défaut (`etat_systeme.veille_claude_code`), lecture seule des fichiers d'état `sessions/<pid>.json` de la CLI (champs `status` busy / idle / waiting, `waitingFor`, `state`), processus vérifié vivant sans lui envoyer de signal. Jamais les transcriptions, jamais les fichiers `*.key` voisins ni les identifiants de compte ; jamais d'écriture. Le format n'est connu que de `interpreter()` derrière `SourceSessions` (testé) : un changement de format donne « état inconnu », pas une panne. Les sessions des worktrees de JARVIS et celles qui nomment un sujet exclu sont ignorées. Alertes : bandeau, voix si choisie, notification du système quand l'interface est cachée (téléphone avec l'interface ouverte ; pas de notification poussée par un service extérieur).

## Mémoire v2 (phase 8, migration 008)

- **Classement v2** (`memoire_v2.classer_v2`, défaut ; `ReglagesRecherche.classement = "v1"` pour l'ancien) : par sous-question, score = (0,6 × hybride + 0,4 × RRF normalisé, k = 60) × (0,85 + 0,3 × importance). La recherche renvoie les deux composantes (cosinus, plein texte) pour cela. La récence reste dans la fusion.
- **Blocs** (`blocs.py`, `memory_blocks`) : courts textes toujours injectés avant le noyau, chaque écriture est une version (`memory_block_versions`) ; `local_uniquement` = jamais vers une IA externe. Le noyau peut devenir les blocs « noyau » et « noyau-prive » : les souvenirs restent, leur tag devient `noyau-converti` (réversible).
- **Oubli** : un souvenir injecté dans une réponse voit `access_count` et `last_accessed_at` mis à jour ; chaque nuit, les souvenirs jamais consultés, peu importants (≤ 0,3), vieux de plus de 180 jours sont **archivés** — jamais ceux dits par l'utilisateur, du profil ou du noyau. Rien n'est effacé.
- **Consolidation** (`consolidation.py`, 3 h 30) : une IA **locale** seulement (sinon ignorée) lit les échanges depuis la dernière consolidation et propose des faits durables (JSON) ; un fait déjà connu (cosinus ≥ 0,92) est ignoré ; un fait sur un sujet privé est rangé privé.
- **Bascule de modèle** : `memoire_vecteurs (memoire_id, modele, vecteur)` garde les vecteurs d'un autre modèle (dimension libre). Changer `JARVIS2_MODELE_EMBEDDINGS` lance au démarrage le calcul en tâche de fond ; la recherche garde l'ancien modèle (`etat_systeme.memoire_modele`) et ne bascule qu'à 100 %. Avant toute bascule, le modèle actif est celui de la majorité des souvenirs.
- **Export** (4 h, ou `jarvis2 memoire exporter`) : `memoire-md/` dans le dossier des données (MEMORY.md, USER.md, SOUL.md, journal/AAAA-MM-JJ.md), en lecture seule.
- **Banc** (`jarvis2 memoire banc --fichier questions.yaml`) : liste de `{question, attendus}` (identifiants ou fragments de contenu) ; rappel@5 et MRR en v1 et en v2. Le fichier reste chez l'utilisateur (données personnelles).
- Les tâches de nuit passent par le planificateur des recettes (`TacheSysteme`, historique `executions_recettes` sous `systeme:<id>`), jamais pendant l'arrêt d'urgence.

## Agents (phase 7, migration 007)

- **Recettes** (`agents/recettes.py`) : fichiers YAML (`nom`, `planification` cron à l'heure de Paris, `consigne`, `connecteur`, `livraison` conversation ou mémoire, `active`) dans `recettes/` à côté de la configuration locale ; relus à chaque battement (30 s), donc modifiables sans redémarrer. Une recette jamais exécutée attend sa première heure après le démarrage (pas de rattrapage en rafale). Historique dans `executions_recettes`. Une recette ne fait que demander une réponse : elle ne déclenche aucune action 🟡 ni 🔴, et rien ne tourne pendant l'arrêt d'urgence.
- **Missions** (`agents/missions.py`, table `missions`) : recherche (plan de requêtes → SearXNG → rapport), brainstorm, revue ; tâche de fond, étapes et progression en base, rapport rangé en mémoire (origine `mission`, privé si le sujet l'est). Les pages web sont transmises entre balises `<donnees>`, déclarées comme données ; la liste des sources est ajoutée par JARVIS, pas par le modèle. Sans SearXNG, le rapport le dit en première ligne.
- **Sujets privés** : `[confidentialite] sujets_prives` (motifs) ou un souvenir `local_uniquement` qui répond au message → le routeur ne propose que des IA locales ; s'il n'y en a aucune, il refuse (le choix explicite d'une IA reste possible). Distinct de `sujets_exclus`, qui retire le sujet de la mémoire injectée.
- **MCP** (`agents/mcp.py`) : client stdio (JSON-RPC 2.0, une ligne par message, protocole 2025-06-18), processus lancé à la demande sans les clés d'API de l'environnement. Chaque outil est inactif par défaut (`outils_mcp`) ; un appel est l'action 🟡 `mcp.appeler` (file d'approbations, audit) ; le résultat est une donnée. Limite connue : l'appel s'exécute dans la transaction de la décision, ce qui tient la base SQLite le temps de l'outil (30 s au plus).

## Stockage : SQLite par défaut, PostgreSQL en option (phase 6)

- **Une interface, deux moteurs** (`db.py`) : le Core n'utilise que `fetch`, `fetchrow`, `fetchval`, `execute`, `acquire` et `transaction` (le sous-ensemble d'asyncpg). `db_postgres.py` enveloppe asyncpg ; `db_sqlite.py` tient **une** connexion sur un fil d'exécution dédié (une requête à la fois, `BEGIN IMMEDIATE` pour les transactions, points de sauvegarde pour les transactions imbriquées, annulation = retour arrière).
- **Requêtes écrites une fois** (style PostgreSQL) et traduites pour SQLite : `$1` → `?1`, conversions `::type` et `FOR UPDATE` retirés ; `now()`, `gen_random_uuid()` et `regexp` ajoutés à chaque connexion. Les durées sont calculées en Python (`datetime.now(UTC) + délai`), jamais par `interval`. Seules la recherche mémoire, le tag noyau et l'audit ont une version par moteur.
- **Types** par les types déclarés du schéma SQLite (`migrations/sqlite/`) : UUID, TIMESTAMPTZ (texte UTC à largeur fixe : l'ordre du texte est l'ordre chronologique), BOOLEAN, JSONB, TEXTLIST et UUIDLIST (tableaux JSON), VECTOR (float32).
- **Recherche** : même score (0,75 × cosinus + 0,25 × plein texte). Cosinus par sqlite-vec (`vec_distance_cosine`), à défaut la même fonction en Python ; plein texte par FTS5 (`unicode61 remove_diacritics 2`, accents et casse ignorés, **sans racinisation française**, mots vides retirés), tenu à jour par déclencheurs.
- **Audit** : SQLite n'a pas de rôles. La chaîne est calculée en Python avec le texte canonique d'`audit_canonique()` (JSON écrit comme `jsonb`) ; des déclencheurs refusent UPDATE et DELETE. Qui a accès au fichier peut retirer un déclencheur, mais toute altération est détectée par `jarvis2 verifier-audit`. Pour une séparation forte (rôle d'audit distinct), utiliser PostgreSQL.
- **Migrations alignées** : chaque migration PostgreSQL a sa jumelle SQLite (même nom). Le schéma SQLite initial (001) contient l'état à la migration 005 ; 002 à 005 sont des marqueurs. SQLite se migre seul au démarrage du serveur.
- **Choix** : `JARVIS2_STOCKAGE` ; vide = PostgreSQL si son mot de passe applicatif est configuré (installation existante), sinon SQLite. L'import `jarvis_v1` passe par une base d'attente PostgreSQL.
- **Copie** `jarvis2 stockage copier --vers sqlite|postgres` (`stockage_copie.py`) : vers une cible vide, tout tel quel (identifiants, dates, vecteurs, empreintes d'audit), plein texte recalculé, contrôles suspendus le temps de la copie ; vérifiée (nombres de lignes, chaîne d'audit, clés étrangères). Testé par aller-retour PostgreSQL → SQLite → PostgreSQL.
- Tous les tests de base tournent sur les deux moteurs (fixture `pool` paramétrée) ; ceux qui portent sur les rôles PostgreSQL restent sur PostgreSQL (`pool_pg`).

## Installation pour tous (phase 6)

- **Paquet** : `uv build --wheel` dans `core` après `npm run build` ; l'interface compilée est livrée dans la roue (`jarvis2/web`), aucun Node à l'exécution. Commande `jarvis2` ; seule, elle migre SQLite, démarre le Core et ouvre l'interface.
- **Scripts** `install.ps1` / `install.sh` : uv (script officiel d'Astral, après confirmation), `uv tool install --python 3.13`, `jarvis2 docteur --reparer`, puis `jarvis2`. Essais : Windows (dossiers isolés, depuis la roue) en 7 min 30 s, dont le téléchargement du modèle ; Linux (conteneur `python:3-slim`) en 15 s. macOS non essayé.
- **Configuration sans fichier** : SQLite, 127.0.0.1:8765. Réglages facultatifs dans `jarvis2.env` du dossier de configuration (installation) ou `.env` du dépôt (développement).
- **Diagnostic** (`diagnostic.py`, `jarvis2 docteur [--json] [--reparer]`, `GET /v1/diagnostic`) : Python, dossier des données, stockage et schéma, interface, modèle d'embeddings, cerveaux, Claude Code, réseau, téléphone, audit, arrêt d'urgence. Réparations automatiques seulement si elles sont sûres : créer ou mettre à jour le schéma SQLite, télécharger le modèle. Le reste donne une commande ou un lien.
- **Assistant de premier lancement** : état dans `etat_systeme` (`accueil`, migration 006) ; une installation existante le voit une fois. Étapes : vérifications, cerveau (page Connecteurs), téléphone, prêt.
- **Accueil de Claude Code** : comme Antigravity, le connecteur ne s'active qu'après un avertissement coché par l'utilisateur (`CONDITIONS["claude_code"]`, versionné) : programme officiel non modifié, abonnement personnel, usage personnel et non commercial, aucun identifiant lu, alternatives (clé d'API Anthropic, Ollama, compatible OpenAI). Il n'est pas « à risque » : le routeur le choisit une fois accepté. Une installation existante doit cocher l'avertissement une fois.
- **Téléphone** : Tailscale, en lecture seule (`tailscale status`, `tailscale serve status`) ; JARVIS ne lance jamais `tailscale up` ni `tailscale serve`, il les propose. Quand le Core est publié (`tailscale serve --bg <port>`), l'adresse `https://<pc>.<réseau>.ts.net` devient une origine autorisée et l'adresse du QR de jumelage. Le premier appareil reste réservé au navigateur du PC (`localhost`).
- **PWA** : manifeste, icônes (192, 512, 180 pour iOS), service worker (pages : réseau d'abord ; fichiers compilés : cache ; `/v1/` jamais en cache). Le navigateur intégré de l'application Claude refuse l'enregistrement du service worker ; Chrome l'accepte (vérifié).

## Stockage PostgreSQL dans un volume Docker

PostgreSQL exige des droits Unix (0700) sur son dossier de données. Un dossier monté depuis un système de fichiers qui ne les gère pas (exFAT, montages Windows via Docker Desktop) est refusé (`initdb: could not change permissions … Operation not permitted`). `docker-compose.yml` utilise donc un volume Docker nommé (`jarvis2_pg`). Pour placer les données sur un autre disque, déplacer le disque virtuel de Docker Desktop (Settings › Resources › Advanced › Disk image location). Le stockage SQLite par défaut (phase 6) supprimera ce besoin pour la plupart des installations.

## asyncpg plutôt que psycopg

Sous Windows, les sous-processus asyncio (CLI `claude`) exigent la boucle Proactor, que le mode asynchrone de psycopg ne prend pas en charge. asyncpg fonctionne avec elle.

## Le prompt de la CLI `claude` passe par l'entrée standard

Windows limite une ligne de commande à 32 767 caractères alors que le prompt peut atteindre 100 000 : il est écrit sur l'entrée standard de la CLI.

## Toujours `stream-json`, et contrôle de la source d'authentification

Seule la sortie `stream-json` émet l'événement `system/init` et son champ `apiKeySource`. JARVIS 2 lit toujours le flux (`generate` le consomme jusqu'au bout) et **refuse** toute réponse dont la source n'est pas `none` (abonnement de l'utilisateur) : une clé API configurée ailleurs ne peut pas basculer JARVIS sur la facturation à l'appel. JARVIS ne lit ni ne transmet jamais de jeton d'abonnement.

## Rôles de base séparés dès la phase 1

`jarvis2_proprio` (migrations) et `jarvis2_app` (Core : données seulement, télémétrie et journal des imports en ajout seul). Le rôle d'audit en ajout seul arrive en phase 4.

## Imports : sources génériques, lecture seule, exclusions locales

`jarvis2/importeurs/` contient une source par outil d'origine. La première, `jarvis_v1`, part d'une **sauvegarde** `pg_dump -Fc` fournie par l'utilisateur (la base vivante de la source n'est jamais interrogée) :
1. restauration dans une base d'attente isolée (`import_jarvis_v1`, refusée au rôle applicatif ; la table des jetons d'accès n'est jamais restaurée) ;
2. copie des tables utiles par le rôle applicatif, en une transaction, identifiants et vecteurs compris, en écartant ce que la configuration locale exclut (`[import.jarvis_v1]` : `exclure_sources`, `exclure_contenus`) ;
3. rapport source / présents / exclus / nouveaux / mis à jour dans la table `imports`.

```powershell
cd core
.\.venv\Scripts\python -m jarvis2 importer jarvis_v1 --sauvegarde <chemin\vers\sauvegarde.dump>
.\.venv\Scripts\python -m jarvis2 verifier-import jarvis_v1
```

L'import est rejouable (rattrapage) : une ligne n'est mise à jour que si elle a changé, un message n'est jamais doublé. La vérification ré-encode un échantillon de souvenirs (même modèle = cosinus 1) et compare les 5 premiers résultats de recherche sur la base d'attente et dans JARVIS 2 pour des requêtes témoins (configuration locale, ou une liste générique).

## Recherche mémoire

`jarvis2/memoire.py` reprend l'algorithme de JARVIS v1 : sous-questions, score 0,75 cosinus + 0,25 plein texte français, fusion, diversité, budgets (10 souvenirs, seuil 0,2, 7 000 caractères, 3 par source), noyau (souvenirs tagués `noyau`, 4 000 caractères). Les souvenirs `local_uniquement` ne partent jamais vers un moteur externe. Les **sujets exclus** de l'utilisateur (`[confidentialite] sujets_exclus` de la configuration locale) sont retirés de tout texte de mémoire injecté au modèle.

## Sécurité (phase 4, migration 004)

- **Appareils** : chaque appareil a son jeton (32 octets aléatoires, `Authorization: Bearer`), dont seule l'empreinte SHA-256 est stockée ; liste et révocation dans l'onglet Sécurité. Toute route `/v1/` l'exige, sauf la santé et le jumelage.
- **Premier appareil** : tant qu'aucun appareil n'a jamais été enregistré, le navigateur du PC (boucle locale, hôte `localhost`) s'enregistre d'un clic. Ensuite : jumelage seulement (code à usage unique valable 5 minutes, montré en QR depuis un appareil autorisé, ou `jarvis2 jumeler` sur le PC).
- **Permissions** : 🟢 exécuté (lecture, retrait d'un accès, arrêt d'urgence) ; 🟡 demande approuvée d'un clic ; 🔴 demande approuvée **uniquement** par une clé d'accès WebAuthn (vérification de l'utilisateur exigée, défi lié à la demande, à usage unique, 5 minutes). Les clés d'accès exigent un nom d'hôte (`localhost`, nom Tailscale…), jamais une adresse IP.
- **Audit** : table en ajout seul, propriété du rôle `jarvis2_audit` (sans connexion), alimentée par `audit_ajouter()` (SECURITY DEFINER) ; déclencheurs contre UPDATE / DELETE / TRUNCATE ; chaîne d'empreintes SHA-256 vérifiable par `jarvis2 verifier-audit` (détecte même une modification faite par un super-utilisateur).
- **Arrêt d'urgence** : annule tout de suite les réponses en cours (la CLI est tuée), puis refuse toute écriture par HTTP 423, sauf ce qui sert à le lever ou à retirer un accès ; l'état survit au redémarrage. Le lever est une action 🔴. Secours de l'administrateur du PC (clé perdue) : `jarvis2 lever-urgence`, qui exige les identifiants du propriétaire de la base et est journalisé 🔴.
- **Filtre** : avant tout moteur externe, chaque texte (consignes, mémoire, historique, message) passe par `securite/filtre.py` (clés d'API, jetons, clés privées, mots de passe, IBAN et cartes vérifiés, n° de sécurité sociale, e-mails, téléphones) ; les réponses d'un modèle local bâties sur des souvenirs privés sont masquées pour les moteurs externes. La conversation stockée et les modèles locaux gardent le texte d'origine.
- **Réseau** : le Core n'écoute que sur 127.0.0.1 ; écouter ailleurs exige `JARVIS2_OUVERTURE_RESEAU=true`, et toute autre origine web doit être déclarée (`JARVIS2_ORIGINES`, liste JSON).

## Connecteurs d'IA (phase 5, migration 005)

- **Une classe, plusieurs connecteurs** : l'identité d'un moteur (id, nom, famille `cli` / `api` / `local`, externe, risque, liens) est portée par l'instance. Le catalogue (`connecteurs.construire_catalogue`) assemble les connecteurs de l'installation à partir de `.env`, de la configuration locale et du coffre.
- **Comptes par CLI** (`moteurs/sousprocessus.py`) : binaire officiel installé et connecté par l'utilisateur ; dossier temporaire vide par appel, effacé ensuite ; environnement sans clés ; prompt sur l'entrée standard ; arbre de processus tué en cas de délai, d'annulation ou d'arrêt d'urgence. Les fichiers d'identifiants ne sont jamais ouverts (test qui surveille toutes les ouvertures de fichiers). Codex : `codex exec --json --sandbox read-only --skip-git-repo-check --ephemeral -`, état de connexion par `codex login status`. Antigravity : `agy -p … --output-format stream-json --sandbox` ; format du flux supposé identique à Gemini CLI, **à confirmer** sur une sortie réelle.
- **Google (compte)** : désactivé par défaut ; activable seulement si la requête porte `accepte: true` et la version courante de l'avertissement (case cochée par l'utilisateur, jamais pré-cochée) ; date et version de l'acceptation gardées en base, audit 🟡 ; une nouvelle version de l'avertissement désactive le connecteur jusqu'à nouvelle acceptation. Le routeur ne le choisit jamais.
- **Clés d'API** : coffre local `coffre.json` à côté de la configuration locale, valeurs chiffrées par DPAPI sous Windows (fichier 0600 ailleurs) ; l'interface ne reçoit que « enregistrée » et les 4 derniers caractères ; aucune clé dans la base ni dans les journaux (test). Coût : celui du fournisseur (OpenRouter), sinon les tarifs de la configuration locale, sinon `cout_inconnu`.
- **Locaux** : Ollama, et serveurs compatibles OpenAI sur leurs ports habituels (LM Studio 1234, llama.cpp 8080, vLLM 8000). Un port peut être occupé par n'importe quel programme : la carte dit ce qu'elle voit (« serveur compatible OpenAI détecté sur… »), et ces serveurs détectés **démarrent désactivés**.
- **Routeur** : choix explicite > choix imposé pour la conversation (`conversations.connecteur`, posé dès que l'utilisateur choisit un connecteur, effacé par « Auto ») > connecteur préféré (`JARVIS2_MOTEUR_DEFAUT`) > compte, puis clé d'API, puis local. Seuls les connecteurs actifs sont sondés au démarrage et par le routeur.
- **Conseil** : experts choisis dans Connecteurs (« Dans le conseil »), sinon jusqu'à 4 connecteurs utilisables non risqués ; avis en parallèle, chacun préparé pour son connecteur (filtre, souvenirs privés) ; synthèse par le routeur, avis transmis comme données ; avis local privé masqué pour une synthèse externe.

## Mémoire v2 préparée sans rien recalculer (migration 003)

- **Modèle d'embedding stocké par ligne** (`embedding_model`) : aucune dimension n'est supposée dans le code ; la recherche ne compare que les vecteurs produits par le modèle de l'encodeur actif. Passer à un autre modèle (ex. `BAAI/bge-m3`, 1024 dimensions) = ajouter une colonne de vecteurs (index HNSW halfvec), la remplir en tâche de fond, basculer.
- **Validité temporelle sans DELETE** : `valid_from`, `valid_to`, `superseded_by`, `observed_at` ; la recherche et le noyau ne voient que `valid_to IS NULL AND NOT archived`.
- **Oubli et consolidation** : `importance` (0 à 1), `last_accessed_at`, `access_count`, `archived`, `derived_from`.
- **Blocs éditables** (`memory_blocks`, historique `memory_block_versions`) : créés mais vides ; le noyau reste pour l'instant le tag `noyau` et deviendra des blocs en phase 8.

## Où partent mes données (phase 14 · C15, migration 013)

- `GET /v1/donnees/flux` (`flux_donnees.py`) décrit chaque fonction depuis la configuration **réelle** : connecteurs actifs (et munis de leur clé), SearXNG, sources scientifiques, Open-Meteo, téléchargements Hugging Face, téléphone (Tailscale), ouverture au réseau, serveurs MCP, et ce qui reste sur le PC (mémoire, dictée, voix, interface, écran décrit). Pour chacune : service contacté, ce qui part, ce qui ne part jamais, destination, où le désactiver (section de la vue Réglages ou clé de la configuration).
- La destination est une **catégorie** (`pc`, `reseau`, `internet`, `variable`), jamais l'adresse : ni URL de SearXNG ou d'un point d'accès, ni nom Tailscale, ni lieu de la maison, ni commande ou chemin d'un serveur MCP, ni clé. Un test vérifie qu'aucune de ces valeurs n'apparaît dans la réponse.
- **Accord images** : une image jointe ne part vers un connecteur `externe` qui lit les images qu'après un accord donné une fois **par connecteur** (`connecteurs.images_accordees_le`), tracé à l'audit, révocable dans Réglages › Sécurité › Où partent mes données. Sans accord, le dialogue renvoie l'événement SSE `accord_images` **avant** d'ouvrir la conversation : rien n'est envoyé ni enregistré, l'interface demande l'accord puis renvoie le message. Les IA locales n'en demandent pas.

## Bureau et téléphone (phase 13 · M, migration 017)

- **Protocole `jarvis://`, deux listes blanches** : l'application de bureau (Tauri, greffon `deep-link`, instance unique) n'accepte qu'une action connue (`ouvrir`, `conversation`, `nouvelle`, `ecouter`, `ecran`, `dire`, `decision`, `gadget`), sans identifiant, port ni fragment, 2 048 caractères au plus ; elle ne l'exécute pas, elle le remet à l'interface (`#jarvis=<lien>`), qui le fait vérifier par le Core (`POST /v1/protocole`, `protocole.py`) : paramètres permis seulement, vue connue, UUID valide, caractères invisibles retirés, audit (le texte de `dire` n'est jamais journalisé). Un lien ne fait **jamais plus qu'une action d'interface 🟢** : rien n'est exécuté, approuvé ni envoyé à l'IA ; `dire` préremplit la saisie (texte non fiable, relu et envoyé par l'utilisateur).
- **Raccourcis globaux** voix (Ctrl+Maj+Espace, sinon Ctrl+Alt+Espace) et écran (Ctrl+Maj+Impr, sinon Ctrl+Alt+Impr) : ils passent par le même protocole (`jarvis://ecouter`, `jarvis://ecran`). Le partage d'écran exige un geste dans le navigateur : le raccourci « écran » propose une carte avec un bouton au lieu de capturer seul. Combinaisons choisies pour ne pas voler un raccourci courant d'un éditeur (Ctrl+Maj+E, Ctrl+Maj+V).
- **Gadget de bureau** : petite fenêtre sans cadre, toujours au premier plan, placée en bas à droite (icône de notification › Gadget), sur `/?mode=gadget` de la même interface : état, nombre de demandes, liens `jarvis://` que l'application intercepte. Pas de déplacement à la souris : la page du Core n'a aucune permission native (choix gardé du lot 11).
- **Web Push sans service à configurer** : clés VAPID générées au premier besoin dans le dossier des données (`push/vapid.pem`, 0600 ; jamais en base, dans git ni dans un journal) ; chiffrement RFC 8291 (`aes128gcm`) et jeton RFC 8292 écrits avec `cryptography` (déjà présent via `webauthn`), sans nouvelle dépendance ; contact VAPID = adresse publique du projet. Adresses d'abonnement limitées aux services de notification connus en HTTPS (Google, Mozilla, Apple, Microsoft) : un appareil ne peut pas faire appeler une adresse de son choix par le Core. Abonnement 404/410 retiré tout seul.
- **Appel de décision** : chaque nouvelle demande 🟡🔴 pousse un message **générique** (« 🔴 Décision demandée — <description de l'action> »), jamais le résumé ni les paramètres ; le clic ouvre `/#decision=<id>` (le service worker n'ouvre que des adresses de JARVIS). Oui (clé d'accès WebAuthn obligatoire pour 🔴, inchangé), Non (un clic : refuser protège), Plus tard (rappel poussé 15 minutes après, l'expiration est repoussée d'autant, 3 reports au plus, aucune décision prise).
- **Jamais de déverrouillage** : le registre des actions refuse tout nom contenant `deverrouill` ou `unlock`, et le protocole n'en a aucune ; rien ne déverrouille le PC ni le téléphone, ni à distance ni sur place.
- **« Partager vers JARVIS »** : Web Share Target en GET (`/?partage_titre=…&partage_texte=…&partage_url=…`, rien à intercepter dans le service worker) ; l'interface le confie au Core (`partages`, 200 derniers gardés), nettoie l'adresse et l'affiche comme **contenu non fiable** ; seul un clic l'envoie à l'IA, encadré (`<contenu_recu non_fiable>`, balises du contenu retirées) avec la consigne de n'y suivre aucune instruction. Lien `javascript:`/`data:` gardé comme texte inerte. Les fichiers partagés ne sont pas pris en charge (POST multipart à intercepter : plus tard).
- **Liens de fichiers à usage unique** : seulement les fichiers du dossier `a-envoyer` du dossier des données (chemin vérifié après résolution des liens symboliques) ; code de 256 bits dont seule l'empreinte est gardée, 10 minutes, une utilisation (même si le téléchargement échoue), `/f/<code>` public car ouvert par le navigateur du téléphone, `Content-Disposition: attachment`, jamais en cache.
- **Limite au jumelage** : 5 échecs par source ou 20 au total en 15 minutes bloquent l'échange (HTTP 429, même avec un bon code), audit 🔴 ; la source est l'adresse de la connexion, ou la première de `X-Forwarded-For` derrière `tailscale serve` (proxy sur la boucle locale). Créer un nouveau code depuis un appareil autorisé lève le blocage.

## Amélioration continue (phase 13 · O, migration 018)

- **Une table, un cycle** (`ameliorations.py`, table `ameliorations`) : suggérée (`proposee`) → réalisée dans un atelier (`en_atelier`) → mise en service (`en_service`) → éventuellement retirée (`retiree`) ; ou écartée (`rejetee`, atelier retiré, branche gardée). Chaque suggestion garde son **origine** (`jarvis` : proposée par JARVIS sous une réponse, bloc `proposer_amelioration` du pilotage, gardée d'un clic ; `utilisateur`) et sa **raison**, obligatoire. Pas de doublon ouvert (même titre, même projet).
- **Réalisation** : réutilise les ateliers (`ateliers/`) tels quels : worktree et branche `jarvis/atelier-…` dédiés, autorisations en direct ; la consigne donnée à Claude Code demande des tests et interdit push et fusion. Jamais de travail sur la branche du projet.
- **Aperçu sans rien toucher** : le contenu exact du worktree (non commité et nouveaux fichiers compris) est lu par un **index git temporaire** (`GIT_INDEX_FILE`), comparé au point de départ de l'atelier ; l'arbre git écrit par cet index (`write-tree`) est l'**empreinte** du contenu. Diff borné (200 000 caractères) et passé par le masquage des secrets.
- **Tests** : la commande vient **seulement** de la configuration locale (`[[ateliers.projets]] tests`, `dossier_tests`), jamais du modèle ni du client ; lancée sans shell, sans clé d'API dans l'environnement, 15 minutes au plus, sortie tronquée et masquée ; lancée sur un clic (journalisé), en arrière-plan, inscrite auprès de l'arrêt d'urgence (qui l'interrompt). L'essai garde l'empreinte testée ; un contenu modifié pendant les tests annule la correspondance et l'essai le dit (`contenu_change` : fichiers écrits par les tests et non ignorés par git). Les tests tournent avec `PYTHONDONTWRITEBYTECODE=1` : vu en vrai, les `__pycache__` d'un projet sans `.gitignore` invalidaient chaque essai.
- **Mise en service** 🟡 (`amelioration.mettre_en_service`, jamais « toujours autorisée ») : paramètres et empreinte calculés par le Core (`POST /v1/ameliorations/{id}/mise-en-service`) ; à l'exécution, refus si l'empreinte a changé depuis la demande (l'approbation tombe), si l'atelier travaille, s'il n'a rien changé, ou si les tests configurés n'ont pas réussi sur ce contenu exact. Fusion **locale** par `atelier.fusionner` (commit du worktree puis `merge --no-ff`, projet propre exigé, conflit = annulé) ; commit d'avant et commit de fusion notés. **Jamais de push**.
- **Retour arrière** 🟡 (`amelioration.revenir`, jamais « toujours autorisé ») : `git revert -m 1` du commit de fusion plutôt qu'un `reset --hard` : rien n'est effacé de l'historique, et cela marche même si d'autres commits ont suivi. Projet propre exigé, conflit = annulé. Si rien n'a été commité depuis la mise en service, l'arbre obtenu est **vérifié identique** à celui du commit d'avant ; les tests du projet sont relancés ensuite (résultat gardé à part).
- **Le modèle ne fait que suggérer** : les actions `amelioration.*` ne lui sont pas proposées et sont refusées dans un bloc `demander_action` ; elles se demandent depuis la vue Améliorations. Toutes les étapes sont journalisées (`amelioration.proposee`, `.atelier`, `.tests`, `.rejetee`, demandes et exécutions). Pendant l'arrêt d'urgence, toute écriture est refusée (423) et le service refuse aussi tests, mise en service et retour arrière.
- **Interface** : vue « Améliorations » ; « Réaliser dans un atelier » lance Claude Code (avertissement Claude Code accepté exigé), « Ouvrir sans lancer » ouvre seulement l'atelier. `approuver` / `refuser` émettent l'événement `jarvis2:demande-decidee`, pour que la vue se relise quand la mise en service ou le retour arrière est approuvé depuis la file des demandes.
- **Reporté** : suggestions automatiques de JARVIS sans conversation (par exemple à partir des échecs répétés des recettes ou du diagnostic) ; elles passeront par le même `proposer(origine="jarvis")`.

## Éveil « Dis Jarvis » et conversation vocale (phase 13 · K1, migration 020)

- **Le Core décide, l'interface capte** (`eveil.py`, `POST /v1/voix/ecoute`) : chaque phrase arrive avec ses horodatages de début et de fin pris sur l'horloge de l'appareil (`X-Debut`, `X-Fin`) ; le Core ne les compare qu'entre eux. Une machine à états par appareil (veille → actif : attente de la commande, réponse, relance) vit en mémoire vive du Core ; l'interface lui dit seulement quand la voix de JARVIS s'est tue (`POST /v1/voix/ecoute/evenement`).
- **Éveil en deux étages** : l'étage 1, sans modèle (normalisation, alias des transcriptions de Whisper, mots coupés « jar vis », correspondance floue), ne déclare un éveil certain que pour « Jarvis » bien reconnu en tête de phrase. Tout le reste (alias douteux comme « j'arrive », « Jarvis » au milieu ou en fin de phrase, flou) est un **signal** : seul ce cas appelle le juge d'intention, une IA **locale** (`router(local=True)`, jamais une IA externe, délai de 4 s, réponse OUI / NON). Juge indisponible (Ollama arrêté : jamais démarré) → règle prudente : vocatif en fin de phrase accepté, le reste écarté.
- **Tampon horodaté** (60 s par appareil) : un mot d'éveil coupé en deux par la détection de la parole est recollé si les morceaux sont à moins de 800 ms ; la phrase précédente sert de contexte au juge.
- **Relance sans mot d'éveil** : une phrase qui **commence** dans la fenêtre (6 s par défaut, 2 à 20 s) après la fin de la voix de JARVIS est prise sans « Jarvis ». Une phrase commencée plus de 300 ms avant cette fin est écartée (écho ou parole par-dessus, laissés au lot K2) ; « stop » et « silence » comptent toujours. « Jarvis » seul arme la phrase suivante pendant 8 s. Une réponse jamais refermée par l'interface se referme seule après 3 min.
- **Commandes vocales** : « stop » arrête la réponse et la lecture (fenêtre de relance rouverte), « silence » coupe aussi la voix et met en veille, « c'est tout » / « veille » met en veille. En veille, elles exigent le mot d'éveil.
- **Écoute pendant que JARVIS réfléchit** : le micro n'est plus mis en pause que pendant que JARVIS parle (écho) ; pendant la réflexion, « stop » est entendu.
- **« Dis Jarvis » en fond** : préférence de l'appareil (stockage local), l'écoute démarre avec l'interface. L'application de bureau passe à WebView2 les drapeaux qui empêchent de ralentir ou d'endormir une page cachée, pour que l'écoute continue fenêtre fermée (cachée dans la zone de notification).
- **openWakeWord facultatif** : désactivé par défaut ; paquet `openwakeword` non ajouté aux dépendances (rien n'est installé sans accord) ; modèle « Dis Jarvis » propre à JARVIS (avec les deux modèles de caractéristiques d'openWakeWord) déclaré pour `telechargements` et téléchargé seulement sur un clic. En veille, il écarte avant Whisper les phrases sans mot d'éveil ; indisponible, il est simplement sauté. Le modèle reste à entraîner et à publier (`eveil-v1` des versions du dépôt) : d'ici là, son téléchargement échoue proprement.
- **Mémoire d'ambiance** (désactivée par défaut) : les phrases non adressées restent en **mémoire vive** seulement (jamais en base, oubliées au redémarrage) ; toutes les 10 minutes une IA locale n'en retient que les idées, décisions, tâches et préférences de l'utilisateur, en souvenirs `local_uniquement` (origine `ecoute`, étiquette `ambiance`), puis le texte brut est oublié. Sans IA locale : rien ne part, le texte est oublié après 30 minutes. Les sujets exclus ne sont jamais gardés. Sans reconnaissance du propriétaire (lot K3), la voix d'autrui n'est pas distinguée : casque conseillé, et le texte de l'interface le dit.
- **Migration 020** : seulement la ligne de réglages `eveil` dans `etat_systeme` (ambiance et openWakeWord coupés, relance 6 s) ; aucune table.

## Synthèse vocale et coupure (lot 13 · K2, migration 021)

- **Trois voix au choix** (`synthese.py`, `etat_systeme` clé `synthese`, Réglages › Voix & écoute) : voix de l'appareil (défaut, lue par le navigateur, rien ne passe par le Core), **Piper** (voix neuronale française sur le PC) et **ElevenLabs** (en ligne, clé de l'utilisateur dans le coffre local, jamais renvoyée : seulement « enregistrée » et ses 4 derniers caractères). Changer de voix est 🟡 et journalisé.
- **Piper en processus séparé** : un processus par phrase (au plus 2 en même temps), texte sur l'entrée standard (jamais dans la ligne de commande), fichier WAV temporaire, délai de 30 s puis processus tué ; une erreur de Piper n'atteint jamais le Core et sa sortie d'erreur (qui peut citer la phrase) n'est pas journalisée. La **voix** (`.onnx` + `.onnx.json`, ~63 Mo, dépôt `rhasspy/piper-voices`) passe par `telechargements.py` sur un clic (empreintes SHA-256 vérifiées). Le **programme** `piper` n'est jamais téléchargé ni installé par JARVIS (c'est un exécutable : l'utilisateur choisit de l'installer, `JARVIS2_PIPER`, `<modèles>/piper/` ou le PATH) ; il est appelé avec `--model` et `--output_file`, compris par le programme C++ comme par `piper-tts`.
- **Jamais muet** : l'interface synthétise jusqu'à 3 phrases d'avance (en parallèle) et les lit dans l'ordre (Web Audio : la CSP n'autorise aucun média externe ni `blob:`) ; une phrase que le moteur ne peut pas dire (réponse 204 et sa raison dans `X-Voix-Raison` : un repli prévu, pas une erreur, donc rien de rouge dans la console ; Piper absent, clé refusée, quota, phrase privée ; ou Core injoignable, arrêt d'urgence) est dite par la voix du système. Voix de l'appareil choisie mais aucune voix française locale : Piper prend le relais s'il est prêt. Aucune voix en ligne du navigateur n'est utilisée.
- **Secrets masqués avant toute lecture** (une clé lue à voix haute s'entend) : par l'interface pour la voix de l'appareil, par le Core (`filtre.masquer_secrets`) pour Piper ; « [SECRET : …] » se dit « (secret masqué) ». Pour ElevenLabs, la même barrière que pour une IA externe : secrets ET données personnelles masqués, et une phrase sur un sujet privé ou à laquelle répondent des souvenirs privés (`ServiceDialogue.est_prive`, phrase par phrase) ne part pas et est lue par une voix locale. ElevenLabs figure dans « Où partent mes données » (actif seulement avec une clé et quand c'est la voix choisie).
- **Coupure quand on parle par-dessus** (`coupure.py`, et le même algorithme dans `interface/src/synthese.ts`), en mains libres : trames de 10 ms, 12 trames de suite au-dessus du seuil (une toux ne coupe pas). Avec annulation d'écho (APM de WebRTC par `livekit` s'il est installé côté Core ; dans le navigateur, celle de `getUserMedia`, WebRTC elle aussi), on décide sur le micro nettoyé, le délai haut-parleur → micro étant **mesuré** par intercorrélation des enveloppes. Sans annulation d'écho : RMS du micro contre RMS du haut-parleur décalé du délai et multiplié par le couplage appris, avec une marge ; un **casque** (nom du périphérique, ou couplage quasi nul mesuré) ramène à un seuil simple. Une coupure fait comme « stop » (lecture et réponse en cours arrêtées) et signale aussitôt au Core la fin de la voix de JARVIS (`parole_fin`, lot K1) : la phrase dite par-dessus entre dans la fenêtre de relance, sans « Jarvis ». « stop » et « silence » eux-mêmes restent décidés par le Core (lot K1) ; ils ne partent jamais à l'IA. `livekit` n'est pas une dépendance : rien n'est installé sans accord.
- **Limite connue** : le début de la phrase dite par-dessus (le temps de la décision, ~150 ms) n'est pas enregistré ; pour « stop » c'est sans effet (la coupure suffit), pour une question il peut manquer le premier mot.

## Niveaux de confidentialité, porte de rappel, changement d'avis (phase 14 · C14, migration 024)

- **Trois niveaux** (`public`, `semi_prive`, `prive`) sur `memoires` et `memory_blocks`, dans une colonne `niveau` à côté de `confidentialite`, gardée : `prive` ⇔ `local_uniquement`, synchronisés par le code, si bien que tout ce qui écrit déjà `local_uniquement` continue de marcher. Défauts : souvenir semi-privé (public s'il porte le tag `noyau`), bloc public.
- **Ce qui sort** est décidé par une seule table, `memoire.VERS_EXTERNE` : noyau, blocs et nouveautés → public ; recherche → public et semi-privé ; privé jamais. Les requêtes et le texte de « Où partent mes données » (`GET /v1/donnees/flux`, clé `memoire`) en sont générés. Un semi-privé ne part donc que lorsqu'il répond au message, jamais injecté d'office ; tout texte externe reste expurgé (sujets exclus) puis masqué (`securite/filtre.py`).
- **Conséquence assumée** : les « Nouveautés de ta mémoire » envoyées à une IA externe ne contiennent plus que des souvenirs publics (presque rien tant que l'utilisateur n'en passe pas en public) ; en local, rien ne change.
- **Porte de rappel sans LLM** (`rappel.py`) : message vide, commande `/`, politesse ou acquittement seul, moins de 4 lettres → pas de recherche ; mention de la mémoire, question, première personne, et dans le doute → recherche. Le noyau et les blocs restent injectés. La raison va dans la méta du message (`porte`). `est_prive` force la recherche, pour que le choix d'une IA locale ne dépende jamais de la porte.
- **Changement d'avis** : `memoire.remplacer` crée le nouveau souvenir (même type, tags, origine, niveau) et clôt l'ancien (`valid_to`, `superseded_by`), dans une transaction ; rien n'est effacé, `versions` remonte la chaîne. Détection déterministe (`contradiction.py`) : même type (fait, préférence, décision, note), cosinus ≥ 0,7, puis marqueur de changement absent de l'ancien (« désormais », « finalement », « en fait », « ne … plus », « au lieu de »…) ou même clé (« je préfère », « j'habite », « mon X est »…) avec une autre valeur ; mots identiques = doublon. La consolidation remplace au lieu d'ignorer. Le seuil 0,7 est calé sur l'encodeur des tests : à revoir sur le vrai modèle si des remplacements manquent ou débordent.
- **Interface** : le niveau est un `<select>` natif (pastille et sélecteur à la fois, clavier sans code en plus), mis à jour tout de suite et remis en cas de refus du Core ; changer le niveau d'un bloc crée une nouvelle version du bloc.

## Voix : transcription, propriétaire, latence, dictée (phase 13 · K3, migration 022)

- **Un transcripteur qui remplace l'ancien** (`transcription.TranscripteurRobuste`, même méthode `transcrire`) : les routes existantes (`/v1/voix/transcrire`) et celles des autres lots voix en profitent sans changement. Chargeur, VAD, détection de la carte, décodeur et horloge s'injectent : tout se teste sans modèle.
- **Carte graphique** : CTranslate2 décide (`get_cuda_device_count`) ; une carte AMD vue par CTranslate2 est annoncée « ROCm » (à mesurer : les roues PyPI de CTranslate2 n'ont que CUDA), une carte AMD non vue est signalée avec la raison. Les bibliothèques CUDA manquent souvent sous Windows : un échec au chargement **ou au premier calcul** fait repasser sur le processeur, sans perdre la phrase. `beam_size` 5 sur la carte, 1 sur le processeur ; `condition_on_previous_text` coupé (moins de boucles).
- **Le modèle par défaut reste « base »** : passer à « small » forcerait un nouveau téléchargement aux installations existantes ; l'état de la transcription et le diagnostic conseillent small ou medium.
- **VAD avant Whisper** : Silero (fourni avec faster-whisper, aucun téléchargement) ; sans parole, Whisper n'est jamais appelé — première cause des phrases inventées.
- **Filtres d'hallucinations** sur le texte sans accents : génériques de sous-titres (« Sous-titres réalisés par la communauté d'Amara.org », « Sous-titrage ST' 501 », Radio-Canada), appels à s'abonner, « merci d'avoir regardé », invite recopiée ; segments `no_speech_prob > 0,6` avec `avg_logprob < -0,7`, `compression_ratio > 2,4` ; répétitions réduites à une ; « Merci. », « Au revoir. »… seuls sur moins de 0,6 s de parole. La raison de chaque segment écarté est rendue (`ecartes`).
- **Disjoncteur** : 3 échecs de suite du modèle (pas un modèle absent, pas un enregistrement trop long) → 60 s de pause (HTTP 503 immédiat), puis un essai ; un nouvel échec rouvre.
- **Transcription anticipée sans état partagé avec l'interface** : le Core garde les 6 dernières anticipations (90 s) avec leurs octets ; un enregistrement final qui **commence par les mêmes octets** (MediaRecorder ajoute des morceaux) et dont la fin ne contient aucune parole (VAD) reprend le texte. Rien à ajouter aux appels existants. L'interface (mains libres) anticipe à 0,3 s de silence et coupe tout de suite si la fin de tour est sûre (≥ 0,8), sinon attend toujours 0,9 s.
- **Fin de tour** : règle d'abord (mot de liaison, article, « euh », virgule ou points de suspension en fin → pas fini ; « ? » ou « ! » → fini) ; le petit modèle n'est consulté qu'entre 0,3 et 0,7, avec 0,2 s pour se connecter et 0,6 s en tout, `keep_alive` 30 min, sans raisonnement. Ollama arrêté = la règle seule, jamais de démarrage.
- **Reconnaissance du propriétaire** : ECAPA-TDNN 512 de WeSpeaker (Apache-2.0, ONNX, onnxruntime déjà présent) plutôt que SpeechBrain (PyTorch, plusieurs Go). Caractéristiques calculées en numpy (80 bandes mel, 25 / 10 ms, fenêtre de Hamming, moyenne retirée) ; inscription et vérification passent par le même calcul. Score = meilleure similarité cosinus parmi les empreintes (10 au plus, 3 s de parole pour en créer une, 1 s pour vérifier), seuil 0,5 réglable de 0,3 à 0,8. Empreintes dans `voix/empreintes.json` du dossier des données (vecteurs seulement), hors base et donc hors copies PostgreSQL ⇄ SQLite.
- **Fermée, sans dépendre de l'interface** : chaque transcription est notée (texte normalisé, verdict, 2 minutes). Une commande rapide dont la phrase reprend une transcription récente (égale, ou l'une contient l'autre à partir de 8 caractères), ou toute demande annoncée par l'en-tête `X-Jarvis-Voix: 1`, est « venue de la voix ». Reconnaissance activée : 🟡🔴 venues de la voix acceptées seulement si « reconnu » ; sinon refus (`voix.action_refusee` à l'audit), y compris modèle absent ou sans empreinte. Les 🟢 et ce qui est fait à l'écran ne changent pas. Limite assumée : une phrase tapée identique à une phrase dite dans les 2 minutes est traitée comme dite.
- **Latence** : `jarvis2 docteur` ne charge rien (deux requêtes vers Ollama, lecture de l'état) ; `--latence` est la demande explicite qui préchauffe et mesure (le modèle Ollama est chargé et gardé 30 min ; Ollama n'est jamais démarré). « localhost » dans `JARVIS2_OLLAMA_URL` est signalé (IPv6 d'abord sous Windows).
- **Dictée : la coque prévient, le Core colle** : l'application de bureau ne fait qu'émettre `jarvis2:dictee` (« debut » / « fin ») dans la page, sans prendre le focus ; l'interface enregistre (350 ms au moins), le Core transcrit, applique la ponctuation dite, les corrections (mot entier, sans casse ni accents, les plus longues d'abord), la mise en forme selon le programme au premier plan, et colle : presse-papiers (texte) remplacé, attente que Maj / Ctrl / Alt / Windows soient relâchés (1,5 s au plus, sinon Ctrl+V deviendrait un collage spécial), Ctrl+V, ancien texte remis après 0,4 s. Aucune dépendance Rust ajoutée. Collage refusé à distance (`est_local`) et en mode sans écran ; le texte dicté n'est jamais journalisé (programme, style, nombre de caractères seulement).
- **Raccourci Ctrl+Alt+D** (sinon Ctrl+Maj+Alt+D) plutôt que Ctrl+Maj+D, pris par plusieurs éditeurs et navigateurs ; il est réservé dès le lancement de l'application de bureau, même dictée désactivée (la coque ne lit pas les réglages).
- **Reporté** : flux « reconnaissance du propriétaire » et « fin de tour » dans « Où partent mes données » (tous deux sur le PC) ; essai réel de ROCm sur une carte AMD ; collage hors Windows.

## Routeur par type de tâche (phase 14 · B 11, migration 028)

- **Quatre types** : code, raisonnement, rapide, privé. Un seul module (`routage.py`) classe, choisit et mesure ; `Connecteurs.router` reste le seul endroit qui filtre (actif, disponible, jamais « à risque », jamais au plafond), il reçoit seulement une préférence et des exclusions.
- **Règles d'abord**, petit modèle seulement en cas d'hésitation (aucun signal, ou égalité en tête) : le classement est instantané et explicable dans l'immense majorité des cas. Le petit modèle Ollama est **facultatif et désactivé par défaut** (l'utilisateur le choisit parmi ses modèles installés) ; il n'est consulté que si Ollama répond déjà à une sonde, 8 s au plus, jamais démarré. Sans lui : rapide jusqu'à 200 caractères, raisonnement au-delà, et la raison le dit.
- **Privé avant tout** : décidé par `ServiceDialogue.motif_prive` (mêmes critères qu'`est_prive`, avec la raison) avant les règles ; la route privée ne prend qu'une IA de famille `local` et non externe (préférence externe refusée par l'API, ignorée si elle existait, double garde après le choix). Aucune IA du PC : refus plutôt qu'une fuite, comme avant.
- **Le score ne mesure que les choix du routeur** : un choix explicite ou imposé par conversation n'a pas de route et ne compte pas. La route voyage dans `Options.route` jusqu'à `MoteurInstrumente`, qui l'écrit dans `telemetrie.meta` (y compris pour une erreur), sans variable de contexte qui fuirait vers les titres automatiques.
- **Formule** : `100 × succès / (succès + erreurs) × (0,7 + 0,3 × min(1, latence cible / latence moyenne)) × (2 + 👍) / (2 + 👍 + 👎)`. La latence pèse au plus 30 % (une réponse lente mais juste reste utile) ; les avis sont lissés (un seul 👎 donne 67, deux 50). Latences cibles : rapide 10 s, code et privé 60 s, raisonnement 90 s.
- **Rétrogradation** : au moins 5 réponses mesurées sur 7 jours et un score sous 60. La route suivante prend le relais ; si toutes les IA possibles sont rétrogradées, la préférée répond quand même (mieux qu'un refus) et le pied le dit. Les transitions sont notées une seule fois (historique de 30 lignes dans `etat_systeme`, audit `routage.retrogradation`). Reprise automatique quand le score remonte ou que les mesures sortent de la fenêtre ; « Rétablir » (🟡, audité) ignore les mesures d'avant.
- **Avis de l'utilisateur** dans `telemetrie` (`operation = 'retour'`, statut `positif` / `negatif` / `retire`, le dernier par message compte) : la table reste en ajout seul pour l'application ; l'avis est aussi gardé dans la méta du message pour l'affichage. Les coûts ignorent ces lignes. Seule une réponse routée peut être notée.
- **Aucune nouvelle table** : réglages, rétablissements, rétrogradations actives et historique dans la clé `routage` d'`etat_systeme`, créée par la migration 028 et écrite par UPDATE seulement. La migration élargit les contraintes `CHECK` de `telemetrie` (`operation` : `retour` ; `statut` : `positif`, `negatif`, `retire`) ; SQLite ne sachant pas modifier une contrainte, la table y est reconstruite à l'identique, données gardées.

## Widgets générés à la demande, phrase d'attente (phase 14 · D 16, migration 029)

- **Même chemin que le bloc d'actions** : le modèle écrit `<widget titre="…">fragment</widget>` ; le Core retire le bloc du texte (il n'est ni affiché brut ni lu à voix haute ; l'interface le masque déjà pendant le flux) et valide le fragment avec `html.parser` de la bibliothèque standard. Pas de « réparation » : un fragment qui contient quoi que ce soit hors des listes fermées (balise, attribut, forme d'une valeur, classe, adresse, commentaire, CDATA, imbrication de plus de 8 niveaux, plus de 200 éléments, 4 000 caractères) est écarté **entier**, avec une raison qui ne recopie jamais le contenu refusé. Un fragment accepté est **réécrit** depuis l'arbre analysé (texte et valeurs échappés) : l'interface ne reçoit jamais les octets du modèle.
- **Défense en profondeur côté interface** : DOMPurify avec les mêmes listes (`ALLOWED_TAGS`, `ALLOWED_ATTR`, aucune donnée ni aria libre, adresses `^#`), plus un crochet `uponSanitizeAttribute` qui revérifie la forme des valeurs, les classes et la vue visée ; le moindre retrait (`DOMPurify.removed`) refuse le widget. Le résultat est un `DocumentFragment` relu nœud par nœud et recréé par React, balises et attributs revérifiés une troisième fois : **jamais d'`innerHTML`** (règle ESLint inchangée). Sans DOM ou si DOMPurify n'est pas pris en charge, tout est refusé. Un test du Core vérifie que les listes de `widgets.py`, de `widgets.ts` et les classes de `widgets.css` restent identiques.
- **Un widget n'agit pas** : ni script, ni formulaire, ni image, ni adresse externe (pas de pistage, pas de fuite). Le minuteur est un `<time data-minuteur="secondes">` animé par le code de l'interface ; un lien `#vue` ouvre la vue par le même chemin qu'une action « naviguer » du pilotage. Les données affichées (météo…) viennent du modèle : les consignes lui interdisent d'en inventer.
- **Épinglés** : table `widgets_epingles` (titre, fragment réécrit, empreinte SHA-256 tronquée qui évite les doublons), 12 au plus, fragment **revalidé** à l'épinglage (l'interface ne fait jamais foi) et à chaque lecture (si la liste fermée se resserre, un ancien widget non conforme cesse d'être servi). Lus avec `/v1/etat` (un seul appel au démarrage). L'audit ne garde que le titre.
- **Phrase d'attente** : événement SSE `attente` ({outil, phrase}), phrases fixes écrites par le code (`attente.py`), jamais par le modèle, qui ne disent que ce qui démarre. Émis aujourd'hui au début du conseil d'experts et de la lecture d'images jointes (les deux outils longs du dialogue) ; la phrase remplace « réflexion » et est dite si la lecture à voix haute est active.
- **Reporté** : widgets dans les réponses des recettes et des missions ; réglage pour couper les widgets ; données en direct (météo réelle) — elles demanderaient un connecteur, donc un accord.
